## 1. The project in one page

Life OS exists to support a life with many concurrent directions without forcing those directions into a single productivity funnel. The system externalizes enough context to preserve ideas, resume paused work, choose current commitments, connect knowledge to action, maintain neglected life domains and learn from the difference between intention and reality.

> **MENTAL ANCHOR [ESTABLISHED]**  
> The system is a mirror with memory. It should reduce the need to remember everything, without taking ownership of the choices it helps illuminate.

The architecture is intentionally compositional. Information can remain loose or become structured. Entities gain properties/relations only when useful. Those properties enable capabilities and operations. Ceremonies periodically compress the whole life into conscious choices. Views expose the same underlying structure differently depending on context. Signals surface patterns; the user interprets them.

## 2. The 12 ideas to reload first

1. **System as Mirror.** Detect, compare and suggest; do not silently decide identity, importance or commitment.
2. **Rails, not rigid schedules.** Choose direction and constraints in advance; choose the exact action in context.
3. **Progressive Structuring.** Text can remain text; promote only when identity, reuse, query, lifecycle or operations justify it.
4. **Derive, do not duplicate.** Keep canonical facts; compute secondary state where reliable.
5. **One reality, many views.** Exploration, execution, ceremony and resume are projections, not separate copies.
6. **Project has identity.** It needs evolution, decomposition, operational memory and resumability.
7. **Phase is not a Temporal Period.** Phase says state/focus; Temporal Period says when.
8. **Knowledge is relational.** Concepts can be reused across contexts; contextual state belongs on the application/relation.
9. **Operationality is gradual.** Properties/relations enable capabilities; no need for a giant mandatory Operational schema.
10. **Experience is sampled.** Sessions capture useful samples; Metrics and Observations are optional, not exhaustive logging.
11. **Self-model is revisable.** Values/interests guide reflection but are not immutable axioms.
12. **Past work should reduce future work.** Projects and practice should produce reusable structure/knowledge when generalization is worth it.

## 3. The current model at a glance

```text
Things / information
  Entity - candidate universal identity carrier
  Relation - semantic/contextual connection
  Property/Literal - simple or structured attached information
  Concept - candidate Knowledge-oriented Entity

Intentions
  Idea - Exploration - Commitment - Project
  Goal / Scenario / Milestone / Task / Trajectory

Time & experience
  Session - Temporal Period - Phase
  Metric - Observation - Insight - Practice

Operations
  partial schema -> Capability -> Operation

Interaction
  Ceremony - View - Signal - Suggestion
```

## 4. What is already decided

- System as Mirror; user retains semantic and intentional authority.
- Planning should use rails rather than rigid schedules.
- Planned-vs-Actual is reflective evidence, not failure scoring.
- Structure grows progressively and promotion is user-controlled.
- Reliable derivable information should not be duplicated.
- Phase and Temporal Period remain distinct.
- Inspiration does not need a dedicated first-class type.
- Project deserves Entity-level identity.
- Generic knowledge and contextual project state must remain separate.
- Operationality is capability-driven rather than an all-or-nothing type.
- Self-model remains revisable.

## 5. What is still not decided

- Whether Property is a true primitive or syntactic sugar over Relation + Literal.
- What exactly counts as a Literal / raw content value.
- How rich Relation metadata can become before a relation itself deserves identity.
- How Capabilities are formally inferred or declared.
- Exact ontology of Session, Phase, Goal, Scenario, Trajectory, Commitment and Decision.
- Whether Self is a normal Entity or a special root/context.
- How recurrence/cadence should be represented.
- How secondary domains such as health, bureaucracy, relationships and travel stress the ontology.

## 6. Ceremonies you should remember

| Level | Question it protects |
| --- | --- |
| Annual / Semiannual | What changed in me/life, what mattered, and where do I want the next broad direction to go? |
| Monthly / Bimonthly | What actually received energy, what is active/novel/neglected, and what commitments should govern the next period? |
| Weekly | Given my real availability and energy, what rails and compatible actions should be ready? |
| Daily | What happened, how did it feel, what is worth remembering, and how do I enter tomorrow? |

## 7. Strong case studies to keep in mind

**Solducci:** proves the need for evolving Project structure, Idea/Feature maturation and generic/contextual Knowledge separation.

**Speedcubing:** proves the need for Practice, Session sampling, Metrics/Observations and derived progress without logging every micro-event.

**Crochet:** proves loose inspiration -> Idea -> Project -> Artifact -> reusable Knowledge without requiring a rigid workflow.

**Agrivoltaico:** proves the need for long-lived Exploration, scenarios, knowledge gaps, parking and high commitment thresholds.

**LaGenteStrana / HistoryExplorer:** add collaboration, evolving requirements, delegation and learning synergies.

## 8. Self-model snapshot

Current recurring value themes: autonomy/self-determination; creativity/expression; understanding; growth; human connection; positive empowerment/impact; active participation in society. Current interests span software/technology, economics, knowledge, music, media, games, Rubik's cubes, human interaction/relationships, energy/world equilibria and many creative crafts.

> **IMPORTANT [WORKING]**  
> These are a current descriptive map, not a canonical ranking of identity. Ceremonies should help revise them when lived experience changes the model.

## 9. Where the design stopped

The checkpoint was intentionally frozen immediately before Ontology Minimum v0.1. We have enough real cases and design constraints. The next task is compression: find the minimum primitive model that can express them without special-case proliferation.

## 10. Resume path

1. Read **01 - Life OS Overview** if the global architecture is fuzzy.
2. Read **11 - Decision Register & Open Questions** before changing a concept, so Working material is not mistaken for Established.
3. Open **12 - Ontology v0.1 Entry Point**.
4. Start with Primitive 1: **Entity**. Ask what identity buys us and what can remain text/property/relation.
5. Stress every proposed primitive against Solducci, Speedcubing, Crochet and Agrivoltaico before adding another primitive.
6. After the strong cases pass, test health, relationships, bureaucracy, travel and recurring maintenance.

> **NEXT ACTION [OPEN]**  
> Continue with Ontology Minimum v0.1 - Entity. Do not jump to database, app framework, graph technology or UI before the conceptual stress test.
