# 0. Model status and scope

| **WORKING** | La distinzione One reality, many views e System as Mirror e consolidata. Le regole concrete di lens selection, signal derivation, ranking e explainability devono ancora essere progettate. |
|-------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

Il Life OS deve poter mostrare molta complessita senza presentarla tutta insieme. Views selezionano il dettaglio utile; signals rendono visibili pattern derivati; suggestions propongono interpretazioni o azioni senza imporle.

# 1. One reality, many views

| **Established principle** Una view non e una copia della struttura. E una proiezione filtrata, ordinata e arricchita della stessa realta sottostante. |

# 2. Lens dimensions

## 2.1 Focus width

| Person -\> Area -\> Project -\> Milestone -\> Phase -\> Task |
|--------------------------------------------------------------|

**Il focus determina quanto contesto laterale mostrare.** Una ceremony annuale richiede larghezza ampia; uno slot di 30 minuti richiede dettaglio stretto.

## 2.2 Temporal distance

| Vision / distant future -\> Milestone -\> Near goal -\> Current phase -\> Task |
|--------------------------------------------------------------------------------|

Maggiore distanza -\> maggiore astrazione. Minore distanza -\> maggiore azionabilita e dettaglio.

## 2.3 Mode

| **Mode**        | **Preferred emphasis**                                            |
|-----------------|-------------------------------------------------------------------|
| **Exploration** | Questions, unknowns, scenarios, resources, validation thresholds. |
| **Study**       | Concepts, resources, gaps, review and distillation.               |
| **Execution**   | Tasks, blockers, next actions, outputs.                           |
| **Practice**    | Sessions, metrics, observations, current skill focus.             |
| **Reflection**  | Planned vs actual, observations, insights, values.                |
| **Maintenance** | Due items, recurrence, risk, readiness, neglected areas.          |

## 2.4 Activity / inactivity

- Recently active -\> compact execution-oriented projection.

- Moderately inactive -\> add context and current phase.

- Long inactive -\> resume view with history, decisions, structure and next step.

- Long inactive + important -\> stronger attention signal.

# 3. Project Resume / Vitrine

**Una Project page deve ricostruire identita e stato con il minimo sforzo cognitivo.** La quantita di informazione dipende dal contesto e dall inattivita.

| **Layer**            | **What it should show**                                                 |
|----------------------|-------------------------------------------------------------------------|
| **Identity**         | Name, short description, current essence.                               |
| **Where I left off** | Current phase, active part, recent decisions.                           |
| **Consolidated**     | Defined structures, stable choices, state of the art.                   |
| **Progress**         | Milestones / current vision completion when useful.                     |
| **Immediate**        | Next actions, blockers, skills/knowledge currently acquired.            |
| **History**          | Structural evolution sufficient for resume, not full content snapshots. |

# 4. Exploration View

- What am I trying to understand?

- What is unknown?

- What alternatives/scenarios exist?

- What knowledge is missing?

- Which resources are trustworthy/relevant?

- What would make me commit, defer or stop?

**La view puo essere attivata dalla current Phase/mode senza cambiare la struttura sottostante.**

# 5. Execution View

- Current goal/milestone

- Ready tasks

- Blockers

- Required tools/context

- Recent decisions

- Output/status

- Next meaningful checkpoint

**L Execution View deve privilegiare actionability senza cancellare l accesso al perche e al contesto.**

# 6. Ceremony View

**Ceremony View ha focus ampio e presenta contesto prima di chiedere decisioni.** Combina summaries, trends, inactive items, maintenance, upcoming events, previous commitments, values/resonance e novelties.

# 8. Signals vs Views vs Suggestions

| **Layer**      | **Meaning**                                                                     |
|----------------|---------------------------------------------------------------------------------|
| **Signal**     | Pattern derivato dal modello: inactivity, imbalance, repeated observation, etc. |
| **View**       | Proiezione con cui le informazioni vengono presentate.                          |
| **Suggestion** | Interpretazione o azione proposta a partire da uno o piu signals.               |
| **Decision**   | Scelta esplicita della persona; non deve essere sostituita da suggestion.       |

| **Key distinction** Signal: "inactive for 8 months". View: "inactive project resume". Suggestion: "keep backlog, archive or resume?". Decision: the user chooses. |
|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|

# 9. Emerging importance

**Una cosa puo diventare importante senza un atto formale iniziale.** Il sistema puo osservare ricorrenza di note, idee, knowledge, links, sessions e ritorni nel tempo.

- Accumulating related Concepts/resources

- Repeated edits/returns

- Multiple projects depending on the same theme

- Increasing time investment

- Repeated appearance in retrospectives

- Growing resonance with current direction

| **WORKING** | L algoritmo di importance deve essere explainable e non sostituire la priorita scelta. |
|-------------|----------------------------------------------------------------------------------------|

# 10. Inactivity signal

**Inactivity deve essere interpretata insieme a importanza e commitment.** La stessa durata puo essere normale per una curiosita e problematica per una visita medica o un progetto esplicitamente committed.

# 11. Imbalance and debt signals

| **Signal family**       | **Example**                                                       |
|-------------------------|-------------------------------------------------------------------|
| **Knowledge debt**      | Resources consumed \>\> knowledge distilled.                      |
| **Action debt**         | Knowledge/ideas grow \>\> experimentation or realization.         |
| **Maintenance debt**    | Recurring life responsibilities neglected.                        |
| **Attention imbalance** | Actual distribution diverges repeatedly from declared intentions. |
| **System debt**         | Life OS maintenance overhead grows without equivalent benefit.    |

# 12. Idea -\> Project signal

- Repeated edits

- Linked resources/requirements

- Time investment

- Tasks or materials appearing

- Clear desired outcome

- Recurring return

| **Suggested mirror** "You are already treating this Idea like a Project. Do you want to promote it?" |
|------------------------------------------------------------------------------------------------------|

# 13. Consolidation opportunity

**Repeated project-specific observations can reveal reusable Knowledge.** Il sistema puo segnalare che una tecnica, lesson o pattern sta riemergendo in piu contesti e potrebbe meritare generalizzazione.

# 14. Repeated observations

**Una singola Observation puo restare locale.** Ricorrenze filtrabili attraverso Sessions e Projects possono diventare materiale per Retrospective o Insight.

| **Example** "In 7 speedcubing sessions hai indicato F2L come bottleneck. Vuoi rivedere la priorita delle milestone?" |
|----------------------------------------------------------------------------------------------------------------------|

# 15. Commitment mismatch

**Il sistema puo mostrare che l allocation reale diverge dalla scelta precedente senza attribuire automaticamente la causa.**

- Plan unrealistic?

- Unexpected obligations?

- Energy constraints?

- A different interest became more resonant?

- Avoidance or blocker?

- The original commitment is no longer desired?

# 16. Value alignment

**Alignment non deve diventare un score morale.** E una lens: quali aspetti che considero importanti sono stati nutriti dalle mie scelte e quali quasi assenti?

| **WORKING** | No automatic value scoring in v0.1. |
|-------------|-------------------------------------|

# 17. Synergies

- Knowledge useful to multiple projects.

- One Project producing tooling for another.

- A Practice revealing design ideas.

- People/relationships connecting domains.

- A Resource relevant to several Concepts.

- An Artifact reusable as pattern/template.

# 18. Suggestion philosophy

- Explain why the suggestion appeared.

- Use evidence visible in the model.

- Keep action user-controlled.

- Allow ignore/dismiss without penalty.

- Avoid repetitive low-value nudges.

- Prefer ceremony-level reflection for ambiguous deep interpretations.

- Escalate urgency only when risk, due date or explicit commitment justifies it.

| **System as Mirror** The system should say "this pattern appears" more often than "you should do X". |
|------------------------------------------------------------------------------------------------------|

## Open questions

- Come selezionare automaticamente la lens senza sorprendere o nascondere informazione importante?

- Quali signals meritano real-time surfacing e quali dovrebbero apparire solo durante ceremonies?

- Come pesare inactivity con importance, risk, commitment e expected cadence?

- Come costruire explainable importance senza un opaque score?

- Come misurare imbalance con dati sufficienti ma poco logging?

- Come gestire suggestion fatigue e user feedback sui signals?

- Quali views devono essere explicit user modes e quali possono emergere dal contesto?
